# 1. 실행계획 읽는 3줄 루틴 (최우선 · 암기 대상)

```
1. Id 0의 A-Rows를 종이 맨 위에 적는다          →  "목표는 몇 건인가"
2. Buffers 열에서 최대값 '리프' Id에 동그라미    →  "범인은 누구인가"
3. 그 Id의 A-Rows ÷ 1번 값                       →  "얼마나 낭비했는가"
```

**이 3줄이면 [1] 병목 판단 40점 중 35점이 확보된다. SQL은 그다음에 읽는다.**

## 1.1 Buffers는 누적값이다 (09-07 최대 수확)

부모 노드의 Buffers에는 **자식들의 Buffers가 이미 포함**되어 있다. 따라서 "가장 큰 Buffers = 범인"이 아니다.

| Id / Operation | 자식 | Buffers | 순수 자기 비용 |
|---|---|---:|---:|
| 1 HASH GROUP BY | 있음(2) | 601,005 | 601,005 − 601,005 = **0** |
| 2 HASH JOIN | 있음(3,4) | 601,005 | 601,005 − (5 + 601,000) = **0** |
| 3 TABLE ACCESS FULL | **없음** | 5 | **5** |
| 4 HASH JOIN | 있음(5,6) | 601,000 | 601,000 − (1,000 + 600,000) = **0** |
| 5 TABLE ACCESS FULL | **없음** | 1,000 | **1,000** |
| 6 TABLE ACCESS FULL | **없음** | 600,000 | **600,000** ← 병목 |

> **블록을 실제로 읽는 것은 테이블/인덱스를 만지는 리프 노드뿐이다.** HASH JOIN·GROUP BY·SORT는 메모리에서 일하며 블록을 읽지 않는다. 그래서 **리프 노드들의 합 = 전체 Buffers** 가 정확히 성립한다 (5 + 1,000 + 600,000 = 601,005).

## 1.2 병목 후보 컷오프

**Buffers 비중 5% 미만은 병목 후보에서 즉시 제외한다.**

09-07 문제3에서 TB_CLAIM(3,200블록, 전체의 0.5%)을 "FULL SCAN이라서" 병목으로 오지목했다. 나눗셈 한 번이면 걸러졌다.

## 1.3 낭비율의 분모는 항상 Id 0의 A-Rows

중간 단계 건수를 분모로 잡으면 문장의 위력이 죽는다.

```
✗  100,000 → 8,333   (폐기 91.7%)     ← 중간 단계
✓  100,000 →    20   (폐기 99.98%)    ← 최종 결과
```

# 2. 조인 방식 판별 — 자릿수 비교법

## 2.1 나눗셈을 버린다

정식 공식은 `손익분기 = 안쪽 테이블 총 블록수 ÷ 4` 이지만, 실제 문제는 경계에 걸리게 출제되지 않는다. **숫자 2개를 나란히 적고 자릿수만 비교하면 된다.**

```
[바깥 건수]        vs        [안쪽 테이블 블록 수]
```

| 상황 | 판정 |
|---|---|
| 바깥이 **훨씬 작다** (자릿수 1개 이상 차이) | **NL + 인덱스** |
| 바깥이 **비슷하거나 크다** | **HASH + FULL** |

## 2.2 검증 — 09-07 출제 5건 전부 자릿수만으로 갈렸다

| 케이스 | 바깥 건수 | 안쪽 블록 수 | 판정 |
|---|---:|---:|---|
| 문제2 · TB_SALES | 6,000 (4자리) | 600,000 (6자리) | **NL** |
| 문제3 · TB_PURCHASE | 30,000 (5자리) | 600,000 (6자리) | **NL** |
| 문제3 · TB_CLAIM | 30,000 (5자리) | 3,200 (4자리) | **HASH** |
| 변형 · TB_PROD | 80,000 (5자리) | 1,000 (4자리) | **HASH** |
| 변형 · TB_CATEGORY | 80,000 (5자리) | 5 (1자리) | **HASH** |

## 2.3 원리 한 줄

```
NL   = 바깥 1건마다 인덱스를 찾아간다   →  비용 ∝ 바깥 건수
HASH = 안쪽을 딱 한 번 통째로 읽는다    →  비용 ∝ 안쪽 블록 수
```

**"찾아갈 횟수"와 "한 번에 읽을 양"의 비교일 뿐이다.**

## 2.4 NL을 고르기 전 필수 점검

**그 조인키로 탈 인덱스가 실재하는가.**

09-07 문제3에서 `NL_AJ`를 지정했으나 TB_CLAIM에 `CUST_ID` 인덱스가 없었고, 신규 인덱스 1개 제약은 이미 소진된 상태였다. 강제 시 30,000 × 3,200 = **9,600만 블록**(AS-IS의 152배)이 된다.

# 3. 집계 위치 판별 — 선집계 vs 후집계

## 3.1 판별 공식

```
집계 입력 건수가  조인 전 > 조인 후  →  후집계 (조인부터)
                 조인 전 = 조인 후  →  선집계 (집계부터)
```

**선집계가 유효한 조건은 오직 하나 — 조인이 건수를 줄여주지 않을 때다.**

## 3.2 판별 절차

실행계획의 A-Rows 열을 아래에서 위로 그대로 옮겨 적는다.

```
필터 후      →  A-Rows  ?
조인 1 후    →  A-Rows  ?     ← 줄었는가?
조인 2 후    →  A-Rows  ?     ← 줄었는가?
GROUP BY 후  →  A-Rows  ?
```

## 3.3 대조 사례 (반드시 함께 기억)

| | 09-07 문제2 (후집계 정답) | 09-07 변형 (선집계 정답) |
|---|---|---|
| 부모 측 필터 | 캠페인 6,000건 **있음** | **없음** (8월 전 상품 대상) |
| 조인 전 → 후 | 500만 → **1만** | 500만 → **500만** |
| 조인의 역할 | 걸러낸다 | **이름만 붙인다** (FK NOT NULL + PK 조인) |
| 정답 | **후집계** + 조인통로 인덱스 + NL | **선집계** 인라인 뷰 + `NO_MERGE` |
| 오답 시 대가 | 300만 명 전체를 미리 집계, 249만 그룹 폐기 | 500만 행을 해시조인 2회 통과 + Temp 298M |

> **조인 상대가 FK NOT NULL + PK 조인이면 탈락 행이 구조적으로 0건이다.** 그 조인은 거르는 게 아니라 이름을 붙이러 가는 것이므로, 500만 행을 통과시킬 이유가 없다.

# 4. 인덱스 선두 컬럼 분별

**"조인키 선두"는 공식이 아니라 NL inner일 때의 결론이다.** 인덱스를 타고 들어가는 주체가 누구인지를 먼저 본다.

| 용도 | 선두 컬럼 | 예시 | 근거 |
|---|---|---|---|
| **NL의 inner (조인 통로)** | **조인키('=')** | `(CUST_ID, SALE_DT)` | 바깥에서 CUST_ID를 들고 찾아 들어감. 고객 1명의 기간 구간이 리프에 연속 배치 |
| **단독 범위 스캔 (커버링)** | **범위키** + 집계 컬럼 포함 | `(SALE_DT, PROD_ID, QTY, AMT)` | 들고 들어갈 값이 날짜뿐. 구간 제한 + 밀도 향상이 곱해짐 |

## 4.1 커버링 인덱스의 이중 효과

| | 테이블 FULL SCAN | 4개 컬럼 인덱스 |
|---|---|---|
| 읽는 구간 | 6,000만 건 전부 | 8월 500만 건만 → **12배 절감** |
| 1블록당 밀도 | 100 rows/block | 220 rows/leaf → **2.2배 절감** |
| 블록 수 | 600,000 | **22,730** (26.4배 절감) |

## 4.2 INDEX 힌트를 쓰기 전 필수 점검

**그 테이블의 SELECT · WHERE · GROUP BY 컬럼이 전부 인덱스에 있는가.**

없으면 **테이블 방문 횟수 = 인덱스가 뽑은 행 수**가 된다. 09-07 문제2에서 `SUM(SALE_AMT)`의 `SALE_AMT`가 인덱스에 없어, 힌트 강제 시 500만 번 랜덤 액세스(AS-IS의 8배 악화)가 발생했다.

# 5. DISTINCT 제거 순서 (결과집합 파괴 방지)

**DISTINCT는 원인이 아니라 결과다. 범인은 증폭시킨 일반 조인이다.**

```
① 증폭 제거 (일반 조인 → EXISTS 세미 전환)   ← 반드시 먼저
② 그 결과로 DISTINCT가 불필요해짐             ← 나중
```

**순서를 바꾸면 결과가 깨진다.** 09-07 문제3에서 일반 조인을 유지한 채 DISTINCT만 제거하여 **10,800건이 150,000건**(고객 1명당 평균 12.5회 중복 출력)이 되었다.

## 5.1 판정 순서 (3줄카드 T04)

| | 확정할 것 |
|---|---|
| ① | SELECT에 그 테이블 컬럼이 **없다** → 존재성(Semi) / 부재성(Anti) |
| ② | 1:N 증폭 여부 → 증폭이면 `EXISTS`/`NOT EXISTS` 전환 → DISTINCT 자동 소멸 |
| ③ | `NOT IN`은 대상 컬럼 NULL 1건에 전건 탈락 → 컬럼이 **NOT NULL인지 DDL에서 확인** 후 `NOT EXISTS` 전환 |

## 5.2 세미조인이 빠른 물리적 이유 — Short-Circuit

일반 NL 조인은 고객 1명당 매칭 12.5건을 **끝까지** 읽는다. `NL_SJ`는 **첫 1건을 만나는 순간 그 고객의 루프를 끊는다.** 그래서 A-Rows가 150,000이 아니라 **12,000(고객 수)** 이 된다.

# 6. 09-07 출제 문항 요약 (표준 정답)

## 6.1 문제1 — 정렬 생략 + Top-N (독립해결 96점)

```sql
CREATE INDEX IDX_ORD_02 ON TB_ORDER (BRANCH_CD, ORD_DT);   -- '=' 선두, 정렬 컬럼 후행

SELECT * FROM (
  SELECT /*+ INDEX_DESC(O IDX_ORD_02) */                   -- '정렬하지 마라'의 문자 표현
         O.ORD_NO, O.ORD_DT, O.CUST_ID, O.ORD_AMT, O.ORD_STAT
  FROM   TB_ORDER O
  WHERE  O.BRANCH_CD = 'B017'
  AND    O.ORD_DT   >= TO_DATE('20260801','YYYYMMDD')      -- TO_CHAR 가공 제거
  AND    O.ORD_DT   <  TO_DATE('20260901','YYYYMMDD')      -- 경계는 '<' (시분초 안전)
  ORDER  BY O.ORD_DT DESC )
WHERE ROWNUM <= 20;
```

**Buffers 100,253 → 24 (4,177배).**
`INDEX`는 "인덱스 써라", `INDEX_DESC`는 **"정렬하지 마라"** — 다른 힌트다.

## 6.2 문제2 — 조인통로 인덱스 + 후집계 (오답 38점)

```sql
CREATE INDEX IDX_SALES_02 ON TB_SALES (CUST_ID, SALE_DT);  -- 조인키 선두

SELECT /*+ LEADING(R C O) USE_NL(C) INDEX(C PK_CUST)
                          USE_NL(O) INDEX(O IDX_SALES_02) */
       R.CUST_ID, C.CUST_NM, COUNT(*) AS SALE_CNT, SUM(O.SALE_AMT) AS SALE_AMT
FROM   TB_CAMP_RESP R, TB_CUST C, TB_SALES O
WHERE  R.CAMP_ID  = 'C2608'
AND    C.CUST_ID  = R.CUST_ID
AND    O.CUST_ID  = R.CUST_ID
AND    O.SALE_DT >= TO_DATE('20260801','YYYYMMDD')
AND    O.SALE_DT <  TO_DATE('20260901','YYYYMMDD')
GROUP  BY R.CUST_ID, C.CUST_NM;
```

**Buffers 636,018 → 58,018 (11배).**
500만 건을 읽는 방법을 개선하려 하지 말고, **500만 건을 읽지 않는 길**을 찾는다.

## 6.3 문제3 — 세미/안티 분별 (오답 38점)

```sql
CREATE INDEX IDX_PUR_02 ON TB_PURCHASE (CUST_ID, PUR_DT);  -- 커버링 → 테이블 액세스 0회

SELECT C.CUST_ID, C.CUST_NM, C.GRADE_CD                    -- DISTINCT 불필요(PK + 비증폭)
FROM   TB_MEMBER C
WHERE  C.GRADE_CD = 'VIP'
AND    EXISTS     ( SELECT /*+ NL_SJ INDEX(P IDX_PUR_02) */ 1
                    FROM TB_PURCHASE P
                    WHERE P.CUST_ID = C.CUST_ID AND P.PUR_DT >= TRUNC(SYSDATE)-90 )
AND    NOT EXISTS ( SELECT /*+ HASH_AJ FULL(M) */ 1
                    FROM TB_CLAIM M
                    WHERE M.CUST_ID = C.CUST_ID AND M.CLAIM_DT >= TRUNC(SYSDATE)-90 );
```

**Buffers 633,200 → 123,200 (5.1배).**
핵심: **한 SQL 안의 두 서브쿼리가 서로 다른 조인 방식**을 가진다 (안쪽 600,000블록 → NL / 안쪽 3,200블록 → HASH).

## 6.4 변형 — 선집계 (미완)

```sql
CREATE INDEX IDX_SALE_02 ON TB_SALE_DTL (SALE_DT, PROD_ID, QTY, AMT);  -- 범위키 선두 + 커버링

SELECT /*+ LEADING(D P G) USE_HASH(P) USE_HASH(G) */
       P.PROD_ID, P.PROD_NM, G.CATE_NM, D.SALE_QTY, D.SALE_AMT
FROM ( SELECT /*+ NO_MERGE INDEX(D2 IDX_SALE_02) */
              D2.PROD_ID, SUM(D2.QTY) AS SALE_QTY, SUM(D2.AMT) AS SALE_AMT
       FROM   TB_SALE_DTL D2
       WHERE  D2.SALE_DT >= TO_DATE('20260801','YYYYMMDD')
       AND    D2.SALE_DT <  TO_DATE('20260901','YYYYMMDD')
       GROUP  BY D2.PROD_ID ) D,                           -- 여기서 500만 → 8만
     TB_PROD P, TB_CATEGORY G
WHERE  P.PROD_ID = D.PROD_ID
AND    G.CATE_CD = P.CATE_CD;
```

**Buffers 601,005 → 약 23,700 (25배)** + Temp 298M 소멸.
바깥 GROUP BY가 사라지는 이유: 뷰에서 이미 PROD_ID 단위로 집계했고 P·G는 PK 조인(1:1)이라 행이 늘지 않는다.

# 7. 답안 제출 전 강제 체크리스트

```
[진단]
□ Id 0의 A-Rows를 적었는가
□ Buffers 최대 '리프' Id를 숫자로 지목했는가
□ 낭비율의 분모가 최종 결과 건수인가

[설계]
□ [바깥 건수] vs [안쪽 블록수]를 나란히 적고 자릿수를 비교했는가
□ NL을 골랐다면 그 조인키로 탈 인덱스가 실재하는가
□ INDEX 힌트 대상 테이블의 모든 사용 컬럼이 인덱스에 있는가
□ 집계 입력이 조인 전/후 중 어느 쪽이 적은지 세었는가

[마감]
□ 결과집합 3문장 — ① 행 수 ② NULL ③ 중복
□ 구문을 전통 콤마 / ANSI 중 하나로 통일했는가
□ 힌트 블록을 낭독하며 인덱스명·별칭 실재를 확인했는가
```

# 8. 30초 퀵-카드

> **🚨 물리적 급소**
> Buffers는 **누적값**이다. 실제로 블록을 읽는 것은 **자식 없는 리프 노드뿐**이며, 리프들의 합 = 전체다.
>
> **⚡ 1초 킬러 공식**
> - 병목 = **Buffers 최대 리프 Id**. 비중 5% 미만은 후보에서 제외
> - 조인 방식 = **[바깥 건수] vs [안쪽 블록수] 자릿수 비교**
> - 선집계 = **조인이 건수를 줄여주지 않을 때만**
> - 인덱스 선두 = NL inner면 **조인키**, 단독 범위스캔이면 **범위키**
> - DISTINCT는 **증폭을 먼저 지워야** 지울 수 있다
>
> **🎬 10초 스캔 시각화**
> ```
> ① Id 0 A-Rows 적기 → ② Buffers 최대 리프에 동그라미 → ③ 나누기
>                        (SQL은 여기서 처음 읽는다)
> ```
